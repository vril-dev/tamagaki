# TAMAGAKI — IoT 組み込みセキュリティエージェント 設計書

---

## 1. 概要

TAMAGAKIはtukuyomi-edgeyをベースにしたIoTデバイス向け軽量Linux組み込みセキュリティエージェントである。  
デバイスに直接組み込むことで、通信経路（インターネット側・LAN内直接アクセス）に関わらず全トラフィックを監視・制御する。L2〜L4 レベルでの介入に加え、アウトバウンド不正監視・IDS を小規模 IoT 環境向けに実装する。

---

## 2. 背景と動機

GW（ゲートウェイ）型のIoTセキュリティ製品には根本的な死角がある。

```
GW型の死角：

[感染PC/攻撃者]
      │
      └── LAN直接 ──→ [IoTデバイス]  ← GWを完全スルー
```

同一LAN内からのL2直接アクセスはGWを経由しないため保護できない。

TAMAGAKIはデバイス自身に組み込むことでこの問題を解決する。

```
[感染PC/攻撃者]
      │
      └── LAN直接 ──→ [IoTデバイス]
                            │
                         TAMAGAKI（内蔵）
                            ├── nftablesで着信フィルタ
                            └── eBPFで異常検知
                       ← どこから来ても守れる
```

また、既存のIoTセキュリティ製品はL7（アプリケーション層）の検査が中心だが、OSレベルから自前で構築することでL2〜L4に直接手を入れられる構成を目指す。

- L2: MACアドレスフィルタリング
- L3: IPファイアウォール（nftables）
- L4: TCP/UDP接続追跡・ポートスキャン検知
- L7: アウトバウンド通信検査・プロトコル検査

## 3. アーキテクチャ

### 3.1 ネットワーク構成

```
┌──────────────────────────────────────┐
│           IoT デバイス                │
│                                      │
│  アプリケーション                     │
│       │                              │
│  ┌────▼────────────────────────────┐ │
│  │     TAMAGAKI セキュリティエージェント  │ │
│  │                                  │ │
│  │  L3  IPファイアウォール・nftables  │ │
│  │  L4  接続追跡・異常検知            │ │
│  │  L7  アウトバウンド監視            │ │
│  │      IDS                         │ │
│  └────────────────────────────────┘ │
│       │                              │
│      eth0                            │
└───────┼──────────────────────────────┘
        │
   [LAN / インターネット]
```

NICは1ポートで成立する。デバイスに相乗りする形で動作する。

### 3.2 パケット処理の流れ

```
NICにパケット到着（着信）/ NICからパケット送出（発信）
       │
       ▼
   XDP hook  ← eBPF: 既知の悪性IPを即ドロップ (L3)
       │
       ▼
   TC hook   ← eBPF: フロー統計・異常検知 (L4)
       │
       ▼
   nf_conntrack  ← 接続状態追跡
       │
       ▼
   tukuyomi (Go userspace)
       ├── アウトバウンド宛先検査
       └── IDSアラート・ルール動的更新
```

### 3.3 技術スタック

| レイヤー | 技術 |
|---|---|
| カーネル内高速処理 | eBPF / XDP / TC BPF |
| ファイアウォール | nftables |
| 接続追跡 | nf_conntrack |
| IDS・監視 | Go + cilium/ebpf |
| パケットキャプチャ | AF_PACKET / gopacket |

## 4. OS 構成

### 4.1 ベース OS

**Buildroot** を採用する。

採用理由:
- ARMクロスコンパイルにネイティブ対応しており、IoT向けハードウェアへの対応が容易
- カーネルconfigを完全に制御でき、eBPF/XDPに必要なモジュールを確実に有効化できる
- rootfsに含まれるパッケージを全て把握できるため、CVEの影響範囲が明確になる
- 不要なモジュールを除去することで攻撃面を最小化できる
- フットプリントが約20〜30MBに収まる

### 4.2 必須カーネル config

```
CONFIG_BPF=y
CONFIG_BPF_SYSCALL=y
CONFIG_XDP_SOCKETS=y
CONFIG_NET_CLS_BPF=y
CONFIG_NETFILTER=y
CONFIG_NF_CONNTRACK=y
CONFIG_AF_PACKET=y
CONFIG_IP_ADVANCED_ROUTER=y
CONFIG_DM_CRYPT=y        # ストレージ暗号化
```

### 4.3 最小 rootfs 構成

```
Buildroot rootfs (~30MB)
├── BusyBox          (init + 基本コマンド)
├── Linux kernel     (eBPF/XDP/nf_conntrack 有効)
├── tukuyomi-edge   (静的バイナリ CGO_ENABLED=0)
├── eBPF プログラム  (.o ファイル)
└── 設定ファイル
```

tukuyomiは静的バイナリとしてビルドするため、glibc等のランタイム依存がなく最小 rootfsでそのまま動作する。

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 \
  go build -ldflags="-s -w" -o tukuyomi-proxy ./cmd/...
```

## 5. ストレージ構成（A/B/C パーティション）

IoT環境は無人運用が前提のため、更新失敗でデバイスが文鎮化しない設計を採用する。

```
ストレージ
├── パーティションA  工場出荷イメージ（原則不変）
├── パーティションB  稼働中OS
├── パーティションC  新イメージ取得・検証用
└── パーティションD  設定領域（IPアドレス等、更新をまたいで保持）
```

### 5.1 通常の更新フロー

```
通常時: Bで稼働中

1. Bが動いたまま Cに新イメージを取得・書き込む
2. 署名検証 OK → ブートローダーに「次は、Cで起動」と指示 → 再起動
3a. C正常起動 + watchdog確認OK → Cを新しい稼働OSとして昇格
3b. C起動失敗 → ブートローダーが自動でBにフォールバック
3c. Bも壊れた場合 → A（工場出荷）にフォールバック、Dから設定を復元
```

### 5.2 watchdog による正常確認

```
C で起動
   │
   ├── 起動後、X秒以内にtukuyomiが「正常」をブートローダーに通知
   │        → Cを正式採用
   │
   └── タイムアウト（通知なし）
            → ブートローダーが、Bに戻す
```

U-Bootのbootcount機能を利用し、起動成功確認前に閾値を超えた再起動回数を検出したら自動でフォールバックする。

### 5.3 A パーティションの保護

Aパーティションはブートローダーレベルで書き込みを禁止し、OSからはアクセス不可とする。  
緊急時（A 自体に重大脆弱性が発覚した場合）のみ、署名付き強制書き換えツールで物理アクセスまたは閉域LAN経由で更新できる抜け道を設計時に用意しておく。

## 6. OTA 更新の仕組み

### 6.1 更新フロー全体

```
[CI/CD パイプライン]
  Buildrootでリビルド
  CVEスキャン (Trivy / Grype) → Critical検出でビルド失敗
  イメージに署名
       │
       ▼
[イメージ配信サーバー (S3等)]
       ▲
       │ pull（定期または手動トリガー）
[tukuyomiエージェント]
  署名検証 → OKならCに書き込み → 再起動
```

### 6.2 設計方針

- デバイスは自分から取りに行く **pull 型** を採用する。管理サーバーからデバイスへのインバウンド穴を開けずに済むためセキュリティ上好ましい。
- 更新は「パッケージ個別適用」ではなく「イメージ丸ごと入れ替え」とする。ルーターのファームウェア更新と同じ思想。
- Aパーティションの更新は頻度が低いため、手動・物理・閉域LANでの対応で許容する。

## 7. セキュリティ設計

### 7.1 多層防御の構成

| 脅威 | 対策 |
|---|---|
| 外部からの直接攻撃 | nftables・eBPFによる着信フィルタ |
| LAN内の他デバイスからの横断攻撃 | デバイス単位でフィルタ（GW型では防げない経路） |
| カーネル脆弱性悪用 | eBPFで悪用パターンの通信を遮断 |
| 物理アクセス | シリアルコンソール無効化・USBブート禁止・ストレージ暗号化 |
| サプライチェーン | 出荷前CVEスキャン・Secure Boot・署名検証 |

### 7.2 ゼロトラストの前提

通信経路を信頼しない設計とする。LAN内からの通信であっても、インターネットからの通信と同様にフィルタリングする。

### 7.3 OTA 更新の扱い

デバイス自身のOTA更新トラフィックはTAMAGAKIが検査・署名検証する。

```
tukuyomi エージェント → [署名検証 + 宛先確認] → メーカーのOTAサーバー
        │
        ├── 署名検証（改ざん検知）
        ├── 宛先ホワイトリスト確認
        └── 不審な更新をブロック
```

## 8. IDS・アウトバウンド監視

### 8.1 検知シナリオ例

```
シナリオ: デバイスが急に未知のIPに通信し始めた

eBPF (カーネル内):
  宛先IPをMAPに記録しながら通過させる

Go (tukuyomi userspace):
  MAPを監視
  「昨日まで通信していなかったIPへの接続」を検知
  → C2通信の疑い → アラート発火
  → eBPFルールを動的更新「このIPをDROPに変更」
  → 以降のパケットはカーネル内で即ドロップ
```

### 8.2 検知項目（初期スコープ）

- ポートスキャン検知（短時間に大量のSYNパケット）
- 未確立接続へのデータ送信
- アウトバウンド宛先のベースライン逸脱
- LAN内の他デバイスへの不審な横断通信

## 9. ハードウェアターゲット

NIC1ポートで動作するため、Linux が動くARMボード全般が対象となる。

| ボード | CPU | RAM | 特徴 |
|---|---|---|---|
| Raspberry Pi Zero 2W | Cortex-A53 | 512MB | 超小型・低消費電力 |
| Raspberry Pi 4 | Cortex-A72 | 2〜8GB | 開発・検証用途 |
| 汎用 ARM SoC | Cortex-A系 | 256MB〜 | 製品組み込み想定 |

eBPF/XDPの動作には、Linux 5.x以上のカーネルが必要。
